# 菜单栏双模式与本机温控

## §1 解决什么问题

用户希望不用反复打开控制窗口，就能查看 Mac 温度、选择全速或按温度自动调节散热器。第一项提供可独立验证的温控 MVP，暂沿用手动启动与首次连接；完整自动运行由 #2 补齐。

来源：[头脑风暴记录](../../../.eo-project/brainstorm/2026-10-31-自动温控与菜单栏.md)。继承全部已钉决定，本项落实双模式、性能取舍和功率边界。

已钉决策：
- 菜单栏点击后提供两个模式按钮，名称为“全速前进”“自动模式”，并明确当前选中项。
- 全速固定请求 36W、最高风扇档 10，不依赖本机温度，不自动回落。
- 自动模式依本机温度动态调整，性能优先、可接受噪声，最高请求 36W。
- 直接替换现有应用层 12V / 水冷组件拦截，不保留新旧限制并存路径；由设备决定是否接受请求。此项由用户明确修订此前要求。
- 保留连接有效性、协议合法性、写入及 ACK 处理；“请求 36W”不等于实测已输出 36W。
- 保留主窗口中的设备信息、灯光和连接日志入口；已有手动制冷设置须先退出自动接管再发送，避免两条控制路径互相覆盖。

建议初值（用户已确认的首版参数）：
- 默认自动模式；首次尚未取得新鲜本机温度时不发送自动制冷设置。
- 每 2 秒采样；温度低于 55℃ 请求 10W / 风扇 4，55～不足 70℃ 请求 18W / 风扇 7，达到 70℃ 请求 36W / 风扇 10。
- 升档使用新鲜有效读数，降档需低于对应升档阈值 5℃ 并持续 20 秒；相同设置不重复发送。
- 超过 6 秒没有有效本机读数，显示“温度不可用”，停止新的自动调节，保留设备最后接受的设置；恢复读数后重新评估。全速模式继续独立工作。

## §2 完成后我应该看到什么

- [x] AC-1 [自动·阻塞] 启动应用后，顶部菜单栏能看到本机温度或“温度不可用”，以及连接/当前模式状态；点击后看到“全速前进”“自动模式”两个按钮，当前模式有选中标记，并能打开原控制窗口。
- [x] AC-2 [自动·阻塞] 设备就绪后点击全速前进，只发送一次最高强度请求（36W、风扇 10）；本机温度变化或失效不会使其降档。没有 12V 或水冷勾选时，应用也不拦截该合法请求。
- [x] AC-3 [自动·阻塞] 点击自动模式后，在 50、60、75℃ 的可控温度序列下分别请求 10W/4、18W/7、36W/10；升温会增强，回落满足 5℃ 回差及 20 秒持续条件才降档，阈值附近抖动不频繁往返切档。
- [ ] AC-4 [自动·阻塞] 读数过期或无效时不会显示为实时温度，自动模式显示暂停原因且不发新自动请求；全速仍可选择。断连、写入失败、拒绝或 ACK 超时均显示真实状态，不宣称设置成功。
- [x] AC-5 [自动·阻塞] 切换模式、连续点击、打开多个窗口时只存在一个控制来源；等待 ACK 时不叠加冲突写入；切换后旧自动任务不再覆盖全速，手动应用设置会退出自动接管。
- [x] AC-6 [自动·阻塞] 本机真实读数来自已核验对应芯片的传感器；在真实负载及回落采样中记录来源、时间与值，缺失时不拿散热器温度或系统热压力冒充。真实设备的请求、ACK 和随后报告档位可对应核查；设备限制或拒绝不误报为满功率。
- [x] AC-7 [自动·阻塞] 原制冷、灯光、状态解析与日志入口可用，现有协议测试通过，应用构建通过；原手动路径同样不再保留 36W 的供电/水冷拦截。

## §3 谁验收、按什么标准

自动项由实施者以可控温度序列、可控时钟及模拟 BLE 结果验证状态机，再在当前 M2 Mac 和可用散热器上验证真实连接/控制路径；不能只测序列化函数或只凭 ACK 判断效果。
运行 ./test.sh 与 ./build.sh，并记录模式切换、拒绝、超时及真实传感器采样证据。设备不可用时，相关 AC 保持未验证，不代勾。
温度来源决策依据见 [M2 调研](../../../.eo-project/research/2026-10-31-m2-temperature.md)，单次探针不构成交付证据。

## §4 不通过怎么办

阻塞项未通过不得归档；代码缺陷回实施修复，传感器来源、阈值或异常策略需实质调整时回草案确认。真实效果不符预期时不以协议 ACK 替代验证。
